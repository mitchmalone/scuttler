# v0.8.5 — a bar that keeps up, and the lighter-shell spike

## Goal

Workspace switches show on the bar in tens of milliseconds again, the bar's idle cost
stops growing with every push site we add, and the "retire Tauri" question gets a
measured answer instead of a hunch — all in one release, which also carries the rename
(v0.8.1 was never cut; DECISIONS 2026-11-04).

## Context

Mitch, 2026-11-04: "Switching Aerospace workspaces takes a long, long time to reflect in
scuttler." Measured on the primary Mac (JOURNAL 2026-11-04):

| Stage                                               | Measured                                  |
| --------------------------------------------------- | ----------------------------------------- |
| `aerospace list-workspaces` (idle and mid-switch)   | 9–60 ms                                   |
| `bar::snapshot()` (aerospace + lsappinfo ×2 + tmux) | 14–47 ms                                  |
| Push loop cadence (fresh process, 175 pushes)       | 1.0 s, max gap 1051 ms, no stalls         |
| Rust push after a switch                            | 590–750 ms (the 1 Hz poll)                |
| Screen repaint after that push                      | ~60 ms                                    |
| `exec-on-workspace-change` → `triggers/workspace`   | **dead**: touches `~/.config/scuttlarr/…` |

The fast path died in the rename: the Desktop rung's generated `aerospace.toml` still
carried `# generated by scuttlarr` and the old trigger path. `rename.rs` moved the home
but never looked at that file, and `is_generated` / `isManagedToml` did not recognise
the `scuttlarr` header, so the rung would not have rewritten it either. Fixed in this
plan (step 2). What the measurements do **not** show is a multi-second stall; the trace
ran on a fresh process. If a long-lived instance degrades (App Nap, timer coalescing on
the sleep-based loop), it was not caught — step 4 removes the sleep loop's dependence
on timers anyway.

The Notion item behind "retire Tauri" is a **time-boxed spike**, not a migration: build
the launcher panel alone on a thinner shell, measure idle RSS against Tauri, write up,
no migration decision inside the spike. `zero-native` is Vercel Labs' Zig shell
(github.com/vercel-labs/zero-native, pre-release; system WebView or CEF; JS bridge
`window.zero.invoke()`). Its floor on macOS is the same WKWebView, and the receipt
counts only the app process: `scripts/mem.sh` read 132 MB for the app while the
WebKit XPC helpers on this Mac (WebContent 98–426 MB, GPU, Networking) are not
attributed to it. A shell comparison that ignores them is meaningless.

## Approach

Fix first, measure second, decide last. Keep Rust boring: the bar stays a listener fed
by Rust pushes; pushes become one serialised stream instead of ten call sites each
spawning four processes. The spike measures the floor before anyone writes a shell.

## Steps

- [x] Diagnose with numbers (sample, trace build, screen-capture timing) — above.
- [x] Fix the dead hook: `rename::migrate` rewrites a generated `aerospace.toml`
      (header and every `.config/<old>/` path) on every boot and asks AeroSpace to
      reload; `is_generated` and `isManagedToml` accept the `scuttlarr` header too.
      Tests: rename (generated follows, foreign untouched), desktop, core.
- [x] Hands-check on this Mac (2026-11-04): after the relaunch `aerospace.toml` reads
      `scuttler`, the trigger file is touched on every switch, and the cells repaint
      162–172 ms after `aerospace workspace N` as seen by a 20 ms screen-capture loop,
      of which ~100 ms is `screencapture` itself.
- [x] The instant path (DECISIONS 2026-11-04): the hook writes
      `$AEROSPACE_FOCUSED_WORKSPACE` into `triggers/workspace`; `bar::push_focus` shows
      the name from the last snapshot in memory before any coalescing or spawn; a bare
      `touch` still works through the full snapshot. Older managed files are upgraded
      at boot (`desktop::boot`). Measured 2026-11-04 (traced build run by hand): file
      write → push 1–15 ms, push itself 0 ms, cells on screen 102–108 ms after
      `aerospace workspace N` by a 10 ms capture loop whose `screencapture` costs ~60 ms
      — the remainder is AeroSpace spawning `/bin/sh` and a WebKit frame.
- [x] One push stream (2026-11-05, DECISIONS 2026-11-05). `bar::push()` is a poke on
      one channel; one thread waits for a poke or the 1 s tick, coalesces the burst
      behind it (30 ms deadline, `drain`), snapshots, evals. A focus the hook reported
      while a snapshot was in flight wins (`settle_focus`, generation counter). An
      unchanged snapshot is not re-sent: the page gets `__barTick()` so its clock
      moves. The snapshot crosses as a JSON string for `JSON.parse`, not an object
      literal. Tests: the coalescer, the focus settle, the script shape.
- [x] Cheaper snapshots (2026-11-05). Front app from `NSWorkspace` (`front_app.rs`:
      `frontmostApplication` on the push thread, plus a `DidActivateApplication`
      observer that pokes, so the cell is instant); the workspace list is cached 5 s
      once the hook has been seen writing `triggers/workspace` in this process, asked
      every tick until then. Spawns per idle second: `aerospace` + `lsappinfo` ×2
      (+ `tmux` per 2 s with the monitor on) → `aerospace` per 5 s (+ the same `tmux`).
      A clean idle CPU number was not possible on this Mac today: seven Claude panes
      were working, their hooks poking the bar; what was measured is below, under
      "What the measuring found".
- [x] Attribute WebKit helpers to the app (2026-11-05): `scripts/mem.sh --webkit` lists
      every process whose kernel "responsible pid" is scuttler (what Activity Monitor
      groups by; `launchctl procinfo` needs root, libquarantine's
      `responsibility_get_pid_responsible_for_pid` does not) with each one's physical
      footprint, then the app's own footprint and its owned-but-unmapped share. The
      receipt stays the app-only number (DECISIONS 2026-11-01); this is the floor
      beside it. Whether the receipt should now include the helpers: Needs Mitch.
- [ ] Spike (2 days, hard stop): the launcher panel alone on (a) bare `objc2` WKWebView
      in an NSPanel from Rust, no Tauri, (b) zero-native. Same panel bundle, same
      reference config, app RSS + WebKit helpers for each, next to the Tauri number.
      Write-up in this plan; no migration code.
- [ ] Decision gate: DECISIONS entry — keep Tauri, thin to wry/objc2, or move the shell.
      Only then does a migration plan exist.
- [ ] Release notes `releases/v0.8.5.md`; receipt and cold start; `scripts/release.sh`.

## What the measuring found (2026-11-05)

Looking for the WebKit helpers turned up the uptime leak ROADMAP "Memory" was waiting
for, far bigger than the 240 MB it had seen (JOURNAL 2026-11-05 has the method):

| Reading, primary Mac, macOS 26.2                  | Instance up 20 h 20 min       | Fresh instance (v0.8.5 build) |
| ------------------------------------------------- | ----------------------------- | ----------------------------- |
| App physical footprint                            | **4036 MB** (RSS 486 MB)      | 41 MB                         |
| …of which owned but unmapped                      | 3660 MB in 78 k regions       | 8 MB, fluctuating             |
| Bar WebContent footprint / CPU / context switches | 1525 MB / 13 min 54 s / 9.4 M | 68 MB / —                     |
| GPU helper CPU                                    | 4 min 20 s                    | —                             |
| App CPU                                           | 14 min 49 s                   | —                             |
| Helpers by responsible pid (`mem.sh --webkit`)    | not measured                  | 440 MB (borders 273)          |

The unmapped memory grew ~1 region (~48 KB) a second while the bar was on and not at
all with it off; it did not track which cells were on, and extra pushes did not add
to it 1:1. In a fresh process the same regions come and go (11–64 at any moment), so
they are in-flight shared buffers between the app and the bar's WebContent that the
old instance had stopped releasing — a WebKit or wry fault in a long-lived view, not
reproducible in minutes. Two things that fed it are gone anyway: the bar's WebContent
was **painting every frame** for every working agent's spinner all day (53 paint
frames in a 5 s `sample` → 0 with `will-change` on the animated glyphs), and every
push re-parsed a 40 KB object literal (20 `JSC::Parser` frames → 1 with diffing and
`JSON.parse`). The leak itself is watched, not closed: `scripts/mem.sh --webkit` on
the launchd instance after a day tells whether the owned-but-unmapped number still
climbs. If it does, the bare-WKWebView arm of the spike is the first place to look
(a plain `WKWebView` in an `NSPanel` either leaks per buffer on this macOS or it
does not).

Workspace switch → cells on screen after the stream: 109–117 ms with the ~60 ms
capture in the loop, the same as before it (98–108 ms); the stream added nothing to
the path a human watches.

## Acceptance criteria

- [x] Workspace switch → bar repaint < 100 ms on the primary Mac, measured (~40–50 ms
      once the capture's own cost is taken out; the capture cannot see finer).
- [x] A pre-rename `aerospace.toml` is repointed on first launch (test + hands-check).
- [x] No out-of-order bar state: one push stream, covered by a unit test on the coalescer.
- [x] Idle spawns per second recorded before → after; fewer after (3/s → 0.2/s, above).
- [ ] Spike write-up with numbers for Tauri, bare WKWebView and zero-native, including
      the WebKit helpers; a DECISIONS entry closes the question either way.
- [ ] `pnpm verify` green; receipt ≤ 120 MB.

## Out of scope

- Migrating off Tauri in this release. The spike decides whether a migration plan is
  written at all.
- AeroSpace's Unix socket (DECISIONS 2026-08-15: off-limits).
- Plugin service cost (ROADMAP Memory).

## Risks / open questions

- The release is still gated on the notary profile (STATUS, rename plan phase 3).
- The multi-second lag Mitch describes was not reproduced on a fresh process; if it
  persists after the hook fix, trace a long-lived instance before step 4 (the trace
  line from this diagnosis is one eprintln in `bar::push`, kept in the JOURNAL entry).
- zero-native is Zig with its own JS bridge; using it would mean driving our Rust
  through a C ABI or rewriting the OS layer. The bare-WKWebView arm of the spike is the
  one that keeps "Rust owns the OS".

Updates panel: three directions for the next iteration

The current build puts the whole report behind a segmented control and tiles borrowed from usage. That shape suits accounts with meters; it blurs the one thing updates needs to show first: which package manager owns which package, and where to click to upgrade all of one.

Design goal: a package manager reads as a unit at a glance, its bulk action sits on it, and a single package is one click. Nothing leaves scuttler.

All three keep the same keys and runner: ↵ or click runs the row, a everything, x cancel, t terminal, r refresh. Mockups show the real report shape from this Mac: Homebrew 3, App Store 1, pnpm clean, mise 1 with gcc upgrading and vips queued.

A

Ledger

recommended

One scrolling list, no view switching. Each manager is a band with its name, count chip, command and its own upgrade all; its packages hang under a gutter rule. A clean manager folds to one line.

WinsEverything visible at once, no mode to switch. Manager bands plus the gutter rule make ownership unambiguous. Bulk-per-manager is one click on the band; the keyboard path is u anywhere inside the group.
CostsWith 40 Homebrew formulae the list is long; bands stay scannable but the panel scrolls. Could cap a group at 8 rows with a +32 more row that expands.
CardSame bands, compact: name, chip, packages. Clean managers collapse to a dim line.
B

Sidebar

two pane

The clipboard-manager split. Managers down the left with counts and state; the chosen manager fills the right with its header, its upgrade all and its packages. ←→ moves between panes, ↑↓ within.

WinsSeparation is structural: a manager is a line on the left, nothing else is. Long Homebrew lists do not push the other managers off screen. Matches the clipboard panel, so the split already exists in the kit (TwoPane).
CostsTwo panes in a 600px panel is tight; package names and version pairs compete for width. One more keystroke to reach a package than A. The run block has to live inside the selected manager's pane or above both.
CardA two-column grid: manager label left, packages right. Reads as a table, dense and tidy.
C

Cards

framed

A summary strip up top with the total and the everything action, then one framed card per manager. The card's title bar carries the name, command, count and its upgrade all; rows sit inside the frame. A clean manager is a one-line frame.

WinsThe strongest separation: a frame and a filled title bar per manager. The summary strip puts the big number and the everything action first, the tools-and-dashboards rule.
CostsHeaviest chrome in the kit so far; the filled title bar is a new idiom (the kit is hairlines, not fills), so it needs a token and a DECISIONS line. Frames eat vertical space on long lists.
CardMini cards. Clear, but busier than the strip's other cards.

What I would pick

A. It fixes the separation with structure the kit already has (section bands, a gutter rule, chips), keeps the whole report on one screen, and puts the per-manager bulk action where the eye lands. B is the right answer if Homebrew lists routinely run past 20 formulae. C is the most legible at a glance but introduces a filled-header idiom the rest of scuttler does not use.

Shared across all three, and worth doing whichever wins: the count chip, the manager's command in dim beside its name, the per-row command as the row's sub line, a clean manager folding to one dim line, and the run block as a one-line meter rather than a stack of tail lines.

  1. Pick A, B or C (or a mix: A's list with C's summary strip is a natural hybrid).
  2. Say whether long Homebrew lists should cap with a +N more row.
  3. Say whether the hover card should list packages at all, or stop at manager · count.
